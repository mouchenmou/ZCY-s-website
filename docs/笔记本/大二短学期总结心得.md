# 大二短学期总结心得

这个短学期对我来说，是一次把“课本上的电路、程序和算法”真正放到一块板子、一个摄像头、一个舵机和一个具体任务里去检验的过程。过去学习专业课时，很多知识点是分开的：C语言是一门课，单片机是一门课，Python是一门课，图像处理又像是另一套体系。但在这次短学期里，它们被压缩到一个连续的实践流程中：第一阶段围绕STM32，从GPIO、定时器、PWM、串口通信到综合实验，训练的是嵌入式系统最底层的控制能力；创意设计要求我们从仿生水下机器人这个真实工程问题出发，完成原型分析、机构方案、建模计算和应用场景论证；第二阶段又转向树莓派、Python、OpenCV、YOLO和GPIO控制，把视觉感知、数据处理和执行机构连接起来。回头看，这个短学期最有价值的地方并不只是完成了几个作业，而是让我第一次比较完整地经历了“感知-计算-控制-验证-反思”的工程闭环。

第一阶段的学习重心是STM32。刚开始接触时，我对STM32的理解还停留在“比普通单片机更复杂”的层面，真正做起来才发现，复杂并不只是因为它有很多外设，而是因为每一个外设背后都有时钟、GPIO复用、寄存器配置、中断优先级、库函数封装等一整套逻辑。课程资料中的《STM32中文参考手册》《Cortex-M3权威指南》《STM32不完全手册_库函数版本》《MiniSTM32开发板原理图》等材料，让我逐渐意识到，嵌入式开发并不是单纯写几行控制语句，而是要知道程序运行在什么内核上，外设挂在哪条总线上，引脚为什么要先开时钟，为什么同一个PA8既可能是普通IO，也可能是TIM1通道输出。以前写程序时，我更关注“代码能不能运行”；经过这一阶段之后，我开始更关注“代码为什么能控制硬件”。

第一阶段的几个作业是逐步递进的。最基础的跑马灯实验看起来只是让LED周期性亮灭，但它让我熟悉了工程模板、头文件包含、GPIO初始化、延时函数和下载流程。通过PA8、PD2等引脚控制LED，我第一次把代码中的GPIO_SetBits、GPIO_ResetBits和开发板上的真实电平变化对应起来。这个实验虽然简单，却是后面所有实验的入口：如果连LED都不能稳定控制，那么后面的定时器、PWM和通信都无从谈起。

定时器实验则把控制从“靠主循环延时”推进到“靠硬件定时与中断”。在TIM3_Int_Init中设置自动重装载值和预分频系数，再在TIM3_IRQHandler中翻转LED，这个过程让我理解了定时器中断的意义。主循环里LED0用delay_ms翻转，而LED1由TIM3中断控制，两种方式的对比很明显：前者依赖CPU不断等待，后者则利用硬件计数和中断机制，在系统运行中按时触发事件。这让我对NVIC优先级、中断标志位清除、定时器更新事件这些概念有了实际印象，也明白了为什么嵌入式系统里不能只靠死循环和延时去处理所有任务。

PWM输出实验进一步把定时器从“定时”扩展到“波形产生”。通过TIM1_PWM_Init配置PA8为复用推挽输出，再不断修改TIM_SetCompare1中的CCR1值，LED亮度不再只是亮和灭，而是可以平滑变化。这个实验让我对PWM的本质理解得更清楚：所谓调光或者舵机控制，并不是直接输出一个“中间电压”，而是在一定周期内改变高低电平所占比例，让负载或执行机构感受到等效控制量。后来第二阶段用树莓派控制舵机时，50Hz PWM和占空比对应角度的关系，其实就是这个知识点在另一块平台上的延续。

串口通信实验让我第一次把单片机和电脑之间的数据通道打通。USART1的TX、RX引脚配置、波特率115200、8位数据、无校验、1位停止位、中断接收和回显，看似是固定流程，但它背后体现的是嵌入式调试中非常重要的一种能力：让设备“说话”。在没有屏幕的单片机系统里，串口输出往往就是最直接的观察窗口。只要能通过串口看到变量、状态和测量结果，后面的调试就会从“猜问题”变成“定位问题”。

综合实验是第一阶段收束得最明显的部分。这个工程把USART1、TIM1 PWM和TIM2输入捕获结合起来，一方面用PWM实现LED0的呼吸渐变，另一方面用WAKE_UP按键的高电平脉宽测量来验证输入捕获。代码中TIM2以1us分辨率计数，上升沿清零并开始等待下降沿，下降沿读取捕获值，同时考虑计数器溢出，最后通过串口输出“WAKE_UP high pulse width”。这个实验让我感受到，真正的嵌入式任务往往不是单个外设孤立工作，而是多个外设配合：定时器负责精确时间，GPIO负责物理输入输出，串口负责反馈，主循环负责状态调度。它也让我对“工程模块化”有了初步认识，比如把PWM和输入捕获分别放在HARDWARE/PWM和HARDWARE/WAKE_CAPTURE中，比所有代码都堆在main.c里更清晰。

在第一阶段中，我最大的收获是对硬件抽象层次的理解。刚开始看库函数时，我会觉得GPIO_Init、TIM_TimeBaseInit、USART_Init这些函数只是固定模板；但通过阅读资料和反复修改工程，我逐渐明白库函数其实是在帮助我们以结构体参数的形式配置底层寄存器。RCC开时钟、GPIO设模式、TIM设预分频、NVIC设优先级，这些步骤不是“玄学顺序”，而是硬件工作所必需的条件。这个认识很重要，因为它让我在遇到问题时，不再只问“代码哪里抄错了”，而是会去想“时钟有没有开、引脚模式对不对、中断标志有没有清、外设是否真正使能”。

创意设计部分是这次短学期中最能体现综合能力的一项任务。课程要求我们完成一份仿生水下机器人设计方案，至少包括生物原型分析、仿生机构方案、建模与计算分析、应用场景设计和可行性分析。我们选择的方案是仿生蝠鲼柔性胸鳍水下机器人Manta-Coral，定位是面向珊瑚礁生态监测的低扰动仿生AUV。这个选题吸引我的地方在于，它不是单纯追求速度或者复杂结构，而是针对传统螺旋桨和舵板推进存在的噪声大、易缠绕、对环境扰动强等问题，尝试用更接近海洋生物运动方式的柔性推进来解决。

在生物原型分析中，我们把蝠鲼的宽大胸鳍、低频拍动、扁平稳定平台和左右胸鳍差动控制作为主要仿生依据。相比普通鱼尾摆动，蝠鲼的胸鳍推进更像“水下飞行”，通过大面积柔性鳍面与水体相互作用产生推进力。这种方式对珊瑚礁生态监测很合适，因为这类任务更需要稳定、安静、低扰动，而不是高速穿越。我们在方案中提出中央密封舱、双侧柔性胸鳍、多舵机相位控制、摄像头和IMU等传感器组合，并考虑用TPU或硅胶膜、碳纤维骨架、亚克力或3D打印密封舱等材料实现。虽然它还是概念方案，但它要求我们把“像蝠鲼”落实到结构、材料、控制参数和应用场景上，而不是停留在外形模仿。

创意设计中最锻炼我的部分是建模与计算。我们用Strouhal数把拍动频率、尾缘摆幅和巡航速度联系起来，用推力和阻力的近似平衡来说明低速巡航的可行性。比如在PPT中，用St=fA/U的关系估算，当频率约1.2Hz、尾缘摆幅约0.08m、目标St取0.30时，速度约为0.32m/s；再通过阻力估算和推力估算说明参数在量级上自洽。这个过程让我意识到，工程设计中的模型不一定一开始就要复杂到CFD仿真，但至少要能回答“参数为什么这么选”“它大概能不能动”“优势和风险在哪里”。模型的作用不是装饰，而是把主观创意变成可以讨论、可以质疑、可以改进的工程方案。

第二阶段的内容从STM32转向树莓派和Python，整体感觉是从“底层外设控制”进入“上层视觉与智能感知”。课程资料先讲树莓派安装配置和远程连接，再讲Python基础、面向对象、数据分析、OpenCV、YOLO和GPIO操作。这个阶段让我感觉很明显：同样是控制硬件，树莓派的开发方式和STM32完全不同。STM32更强调寄存器、时钟、中断和实时性；树莓派运行Linux，可以用Python快速调用OpenCV、Ultralytics、matplotlib、RPi.GPIO等库，开发效率高很多，但也会遇到系统环境、图形窗口、摄像头编号、依赖安装、SSH显示等问题。两者没有绝对优劣，而是适合不同层次的任务。

NumPy作业虽然没有单独放在第二阶段作业文件夹里，但它来自《Python数据分析》最后一页。题目要求创建边界全为1、其余为0的a*a数组t1；创建对角线为1到b的b*b数组t2；创建4*4随机整数数组t3，并提取0轴和1轴最大值、最小值位置拼接成t4；最后令a、b=4，计算t5=t1+t2-t3+t4，将负数替换为0，其余替换为1并转换为一维数组。这个作业看起来像数组练习，但它训练的是数据结构思维：数组不只是表格，而是可以被索引、广播、统计、筛选和重组的对象。后面OpenCV中的图像其实也是NumPy数组，像素坐标、通道、mask、阈值处理都离不开这种数组思维。

OpenCV课后作业要求对视频后半段目标物使用RGB、HSV和直方图反投影三种方法，实现类似泛洪填充效果的目标跟踪定位。我们在track_object.py中自动读取视频，从后半段开始，设置初始ROI，并分别输出rgb_tracking.mp4、hsv_tracking.mp4、hist_backprojection_tracking.mp4以及四宫格对比视频。这个作业让我系统地接触了颜色空间、阈值分割、mask清理、开闭运算、孔洞填充、轮廓提取、目标中心和搜索窗口等图像处理流程。相比只看课件里的API，真正处理视频时会发现问题复杂得多：光照会变，背景会干扰，目标边缘可能不连续，mask里会有噪声，目标丢失后还要尽量在上一帧附近重新找回来。因此程序中加入了中值滤波、形态学操作、面积筛选、位置约束和输出视频对比，这些都不是单个函数能自动解决的，而是需要根据任务逐步调参。

YOLO目标检测实验让我接触了另一种视觉路线。传统OpenCV方法主要依靠颜色、边缘、形态学等人为设计规则，而YOLO把目标检测建模为神经网络推理，可以直接输出类别、置信度和边界框。我们使用YOLOv11n轻量模型进行图片检测和摄像头实时检测，程序中通过Ultralytics加载yolo11n.pt，对图片或摄像头帧进行predict，再用result.plot显示结果。这个实验让我认识到深度学习模型在泛化能力上的优势，也让我看到边缘设备部署时的现实限制：树莓派CPU推理速度有限，实时性不如传统颜色阈值方法；SSH环境下OpenCV窗口可能无法显示；摄像头编号也不一定固定，需要自动遍历VideoCapture。也就是说，AI模型不是一放进去就万事大吉，工程部署时仍然要考虑算力、延迟、显示环境和硬件兼容性。

GPIO、电阻和舵机实验把第二阶段重新拉回硬件控制。舵机测试中，我们用RPi.GPIO在GPIO23和GPIO24上输出50Hz PWM，通过改变占空比控制垂直和水平舵机角度。这个过程和第一阶段STM32 PWM形成了呼应，只是平台从裸机单片机变成了Linux上的Python库。电阻测量实验则通过RC充放电原理，用GPIO控制电容放电和充电，测量电压达到高电平阈值所需时间，再根据电容充电公式反推电阻值，并用matplotlib实时画出变化曲线。这个实验很典型地体现了“数字IO模拟测量模拟量”的思路：树莓派没有直接的ADC，但可以利用时间测量和RC电路间接得到电阻变化。调试过程中也暴露了很多实际问题，比如接线错误会导致测量值异常，电容没有充分放电会造成周期跳动，SSH环境下图形窗口无法显示。最后通过重新检查面包板连接、增加放电等待、多次采样取平均等方法，测量值才逐渐稳定。

第二阶段最综合、也最有挑战的是双轴云台目标追踪实验。这个实验要求摄像头实时获取图像，识别目标位置，计算目标中心和图像中心的偏差，再控制水平和垂直两个舵机转动，使目标保持在画面中心附近。我们最初也尝试过使用YOLO进行目标检测，但在树莓派上推理速度较慢，而且检测框会抖动，导致舵机频繁调整，云台不够稳定。最终我们采用HSV颜色追踪加比例控制的方案：先通过鼠标点击目标颜色，读取该点HSV值，生成一定范围内的颜色mask，再寻找轮廓并计算中心点，根据error_x和error_y调节舵机角度。为了减少抖动，我们加入了坐标指数平滑、死区控制和舵机更新频率限制，例如smooth=0.8*old+0.2*new、DEAD_ZONE=10、每0.1秒更新一次舵机。

这个追踪实验虽然最终实现了目标跟踪，但也留下了很值得反思的不足。首先，我们的颜色模型本质上是从鼠标点击的一个HSV点扩展出来的范围，而不是根据整个物体轮廓或完整目标区域建立稳定特征。虽然后续程序会通过findContours寻找mask中的区域并计算中心，但目标定义仍然过度依赖单点颜色。这样在某些场景下会出问题：如果目标是纯色物体，物体上每个位置颜色几乎一样，单点颜色并不能表达“这是整个物体的形状和边界”；如果背景中有相近颜色，程序也可能把背景区域当成目标；如果光照变化或目标表面反光，单点HSV范围还可能失效。相比之下，如果能基于物体轮廓、区域特征、颜色直方图或检测框进行追踪，目标会更稳定，也更接近真实的“物体追踪”。

其次，舵机运动时抖动明显，有时甚至会出现“抽风”的现象。这一方面来自视觉检测噪声：目标中心在相邻帧中会轻微跳动，经过比例控制后会直接转化为舵机角度变化；另一方面也和舵机本身、供电稳定性、PWM控制精度、机械安装松动有关。我们虽然通过平滑、死区和限频做了一些优化，但还没有真正形成稳定的闭环控制。后续如果继续改进，我认为可以从几个方向入手：使用更稳的目标表示方式，例如轮廓级ROI、直方图反投影、CamShift或轻量检测模型；对舵机控制加入更合理的PID或限速策略，而不是简单比例调节；为舵机提供独立稳定电源，减少电压波动；在机械结构上增加阻尼或提高云台刚度；同时把视觉帧率、舵机更新频率和控制增益一起标定，而不是单独调某一个参数。

这次短学期也让我更加重视调试能力。以前遇到程序报错，我常常会下意识觉得是代码逻辑错了；但这次大量问题都不是单纯的语法问题，而是环境、硬件、连接和参数共同造成的。比如STM32工程中，可能是Keil工程文件没有加入新模块，可能是外设时钟没开，也可能是中断优先级或标志位没有处理好；树莓派中，可能是Python库没装对，可能是SSH没有图形环境，可能是摄像头编号不是0，可能是GPIO编号方式BOARD和BCM混淆；电阻实验中，可能公式没错，但接线方式错了；追踪实验中，算法能跑，但光照、背景和舵机物理特性会让效果不稳定。这些经历让我明白，工程实践里的“错误”往往不在一个孤立点上，而是藏在系统边界之间。

从能力提升的角度看，第一阶段培养的是底层控制的严谨性，第二阶段培养的是快速开发和系统整合能力。STM32要求我理解硬件时序、外设初始化和实时控制，不能随便依赖操作系统和高级库；树莓派和Python则让我看到高层库的强大，几行代码就能打开摄像头、处理图像、加载YOLO模型、绘制曲线、控制GPIO。两种方式结合起来，才比较接近真实机器人系统的构成：底层需要稳定可靠地驱动电机和读取传感器，上层需要处理视觉、决策和交互。创意设计中的仿生蝠鲼机器人方案，其实也正好把这两部分连接起来：STM32可以负责舵机节律和PWM控制，摄像头和算法可以负责生态监测、目标识别和环境感知。

团队合作方面，我也有比较深的体会。创意设计不是一个人凭空想一个造型，而是需要分工查资料、讨论生物原型、确定机构方案、推导模型、制作PPT并准备答辩。第二阶段的线下实验也需要两个人配合：一个人调代码，一个人看硬件反应；一个人检查接线，一个人观察终端输出和图像窗口。尤其是追踪实验，视觉、舵机、电源、机械结构同时参与，单靠一个人盯着屏幕很难快速发现问题。通过合作，我感受到工程任务中沟通的重要性：必须把问题描述清楚，比如“舵机不动”和“舵机抖动”是完全不同的问题；“目标丢失”和“目标中心跳动”也对应不同的解决方向。

当然，这次短学期中我也看到自己很多不足。第一，理论基础和工程实现之间还有距离。比如我知道PWM占空比可以控制舵机，但真正遇到垂直舵机零点偏移时，还是需要反复试duty=1.8、3.0、6.0等实际值才能校准。第二，算法理解还不够深入。OpenCV和YOLO实验让我知道了很多方法，但对不同方法适用场景、鲁棒性和计算代价的比较还不够系统。第三，调参能力还需要提升。追踪实验中，HSV范围、面积阈值、比例系数、死区、更新频率都需要调，如果没有清晰记录，很容易变成凭感觉试。第四，实验报告和代码之间的对应关系还可以更好。以后做项目时，我应该在实验过程中就及时记录每次改动的原因、效果和失败情况，而不是等最后再回忆。

如果以后继续完善这次的项目，我希望能把第一阶段和第二阶段的内容真正融合成一个小型机器人系统。例如，在仿生蝠鲼机器人方案中，可以先做一个简化样机，用STM32产生多路PWM控制柔性胸鳍舵机，实现开环节律摆动；再用树莓派或上位机处理摄像头图像，完成目标识别、路径记录或环境监测；最后通过串口或其他通信方式让上层视觉结果影响下层运动控制。这样，跑马灯、定时器、PWM、串口、OpenCV、YOLO、GPIO就不再只是分散作业，而会成为同一个系统中的不同模块。虽然这样的完整系统难度更大，但这次短学期已经让我看到了它的基本拼图。

总的来说，这次大二短学期让我从“会写一些代码”向“理解一个系统如何工作”迈了一步。第一阶段让我知道，控制一个LED、一个定时器、一个PWM通道和一个串口，并不是小题大做，而是嵌入式系统的基础语言；创意设计让我知道，工程创意必须有原型、有结构、有模型、有应用场景，也要敢于写出风险和改进方向；第二阶段让我知道，视觉识别和硬件控制结合起来时，算法效果必须接受真实环境和执行机构的检验。最终完成这些作业后，我对专业实践的理解变得更具体了：实践不是把知识点机械拼起来，而是在限制条件下不断让方案变得能运行、能解释、能展示、能改进。

这次短学期也让我更能接受工程中的不完美。追踪实验虽然成功了，但HSV单点选色不够稳，纯色物体和相似背景会让目标定义变得模糊；舵机虽然能跟随目标转动，但抖动和抽风说明控制链路还不够成熟。这些不足并不只是扣分点，它们反而提醒我，一个系统从“能动”到“好用”之间还有很长距离。真正的工程能力，不是永远不出问题，而是能看见问题、说清问题、分析问题，并提出下一步改进路径。带着这样的认识结束短学期，我觉得自己对嵌入式、图像处理和机器人系统都有了更扎实的兴趣，也更清楚后续应该往哪里补课：继续加强底层硬件原理，系统学习控制算法和视觉追踪方法，同时养成更规范的实验记录与版本管理习惯。这个短学期很紧凑，也确实辛苦，但它把很多原本零散的知识第一次连成了一条线，这就是我最大的收获。
