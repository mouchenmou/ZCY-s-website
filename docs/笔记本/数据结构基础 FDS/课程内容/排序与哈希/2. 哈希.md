
## 1. 引言与动机——为什么需要哈希？

我们已经有了 $O(\log n)$ 的二分查找，也有了 $O(n \log n)$ 的最优排序。那为什么还需要哈希？

因为**任何只通过比较进行排序的算法，最坏情况都是 $\Omega(n \log_2 n)$**。排序的下界摆在那了，要想进一步突破速度限制，就必须做点**除了"比较"之外**的事情——哈希就是这个思路。

### 1.1 插值查找：用公式猜位置

在进入哈希之前，先看一种"不走寻常路"的查找方法。

前提：表已经排好序。我们不一个一个比，而是**根据目标值猜它应该在哪儿**。

给定已排序列表 `f[l].key, f[l+1].key, ..., f[u].key`，要查找目标 `key`。利用**相似三角形**的比例关系：

$$
\frac{f[u].key - f[l].key}{n} = \frac{key - f[l].key}{i - l}
$$

推导出预估下标 $i$：

$$
i = l + \frac{(key - f[l].key) \cdot n}{f[u].key - f[l].key}
$$

然后：
- 如果 `f[i].key < key`，则 `l = i`（目标在右边）
- 否则 `u = i`（目标在左边）

![](附件/Pasted%20image%2020260615230201.png)

!!! tip "插值查找的意义"
    它和二分查找不同——它**不依赖比较**来缩小范围，而是**用一个公式直接猜下标**。从这个角度看，哈希函数其实就是一种更极端的"直接猜位置"。

## 2. 符号表与哈希表基本概念

### 2.1 符号表（Symbol Table / Dictionary）

!!! conception "定义"
    符号表（= 字典）是一组 `<name, attribute>` 键值对的集合，其中 **name 是唯一的**。

!!! example "生活中的例子：牛津英语词典"
    - `name` = "since"
    - `attribute` = 一列含义：M[0] = 在某日期之后、M[1] = 鉴于……

!!! example "计算机里的例子：编译器的符号表"
    - `name` = 标识符（如 `int`）
    - `attribute` = 使用该标识符的代码行列表及其他字段

**符号表 ADT：**

- **对象**：Name-attribute 键值对集合，name 唯一
- **操作**：
    - `Create`：创建表
    - `IsIn`：检查是否存在
    - `Find`：查找属性
    - `Insert`：插入
    - `Delete`：删除

### 2.2 哈希表物理结构

想象你有一个**大柜子**，柜子有 $b$ 个抽屉（这些抽屉叫 **桶，bucket**），每个桶里还能放 $s$ 个槽（slot）。

- 哈希表（hash table / 散列表）用数组实现这个柜子 `ht[0..b-1]`
- 每个桶有 $s$ 个槽位
- 对标识符 $x$，定义哈希函数 $f(x)$ 表示 $x$ 在 `ht[]` 中的位置（桶的索引）

!!! conception "关键指标"
    设 $T$ 为所有可能的关键字总数，$n$ 为哈希表中当前标识符总数：

    - **标识符密度（identifier density）** = $n/T$
    - **装载密度（loading density）** = $\lambda = n/(sb)$
    
    $\lambda$ 直观理解就是**哈希表被填了多少**：$\lambda = 0$ 表示空表，$\lambda = 1$ 表示全满。$\lambda$ 越大，碰撞概率越高，查找/插入就越慢。后面会看到，很多哈希策略都对 $\lambda$ 有明确的上限要求。

### 2.3 Collision 和 Overflow

!!! example "冲突（collision）"
    两个不同的key $i_1 \neq i_2$，但哈希函数算出来位置一样：$f(i_1) = f(i_2)$。

!!! example "溢出（overflow）"
    一个桶已经满了，还要往里面塞新的关键字。

    当 $s = 1$（每个桶只有一个槽）时，冲突和溢出是同时发生的。

!!! example "PPT 上的例子：把 10 个 C 库函数映射到哈希表"
    **场景：** 将 $n=10$ 个 C 语言库函数映射到 $b=26$ 个桶、$s=2$ 个槽位的哈希表 `ht[]` 中。

    装载密度 $\lambda = 10 / 52 = 0.19$。

    哈希函数：**只看首字母**，$f(x) = x[0] - 'a'$，把 a~z 映射到 0~25。

    **插入过程（按顺序）：**

    | 顺序 | 函数 | 首字母 → 桶 | 结果 |
    |:--:|:--|:--:|:--:|
    | 1 | `acos` | a → 桶 0，Slot 0 | ✅ |
    | 2 | `define` | d → 桶 3，Slot 0 | ✅ |
    | 3 | `float` | f → 桶 5，Slot 0 | ✅ |
    | 4 | `exp` | e → 桶 4，Slot 0 | ✅ |
    | 5 | `char` | c → 桶 2，Slot 0 | ✅ |
    | 6 | `atan` | a → 桶 0，Slot 1 | ✅ |
    | 7 | `ceil` | c → 桶 2，Slot 1 | ✅ |
    | 8 | `floor` | f → 桶 5，Slot 1 | ✅ |
    | 9 | `clock` | c → 桶 2，**满了！** | ❌ **溢出！** |
    | 10 | `ctime` | c → 桶 2，**还是满的** | ❌ **溢出！** |

    **发生了什么？** 桶 2（c 开头）的两个槽位被 `char` 和 `ceil` 占满了，后面来的 `clock` 和 `ctime` 即使还有别的桶是空的也进不去——因为哈希函数只认首字母，它俩只能去桶 2。

!!! tip "没有溢出时的复杂度"
    在理想情况（没有碰撞/溢出）下，哈希表的操作就是"算一下位置，直接读写"：

    - $T_{\text{search}} = T_{\text{insert}} = T_{\text{delete}} = O(1)$

    这就是哈希表被称为**常数时间**数据结构的底气。当然，代价是你要设计一个好的哈希函数，以及合适的冲突解决策略——下面几节就是讲这个。

## 3. 哈希函数——怎样设计一个好用的"魔法函数"

一个好的哈希函数要有三个特点：

1. **算得快**——不能比直接比较还慢
2. **冲突少**——尽可能减少碰撞的可能性
3. **无偏（unbiased）**——每个桶被命中的概率相等

!!! conception "均匀哈希函数（uniform hash function）"
    对所有关键字 $x$ 和所有桶 $i$，$P(f(x) = i) = 1/b$。这种理想的哈希函数称为均匀哈希函数。

!!! tip "为什么哈希函数最后都要 `mod TableSize`？"
    因为哈希表是一个数组 `ht[0..b-1]`，而哈希函数算出来的原始值可能非常大（比如字符串移位算出一个几亿的数），**直接拿它当下标就越界了**。`mod TableSize` 就是把这个值**限定在 [0, TableSize-1] 范围内**，保证不会访问到数组外面去。

    这一点对所有哈希方法都成立：不管是取模哈希、线性探测、二次探测还是双重哈希——最后一步一定是 `mod TableSize`。

### 3.1 整数哈希：取模法

对整数做哈希，最经典的方法就是取模：

$$f(x) = x \bmod \mathrm{tableSize}$$

!!! warning "陷阱"
    假设 $\mathrm{tableSize} = 10$，而存入的 $x$ 全部以 0 结尾（比如 10, 20, 30, ...）——那所有值都会掉进同一个桶，哈希表直接退化成链表。

!!! tip "解决方案"
    TableSize 最好选**质数（prime number）**。比如 tableSize = 10 时，所有偶数的 x 都落在偶数桶里——但 tableSize = 11（质数）就没有这种模式，分布均匀得多。

### 3.2 字符串哈希

对字符串做哈希比整数麻烦得多。关键问题是：**怎么把一个字符串压缩成一个整数下标？**

#### 方法一：把所有字符的 ASCII 值加起来（很差的方法）

$$f(x) = \left(\sum x[i]\right) \bmod \mathrm{tableSize}$$

!!! problem "问题在哪？"
    设字符串长度 $\leq 8$，ASCII 值 $x[i] \in [0, 127]$，那么 $f(x)$ 最大只有 $8 \times 127 = 1016$。

    如果 tableSize = 10007，结果呢？**$f(x)$ 永远只能落在 [0, 1016] 之间，剩下的 9000 多个桶全是空的**——空间利用率不到 10%。而且所有"和相等"的字符串（比如 "abc"、"cab"、"cba" ASCII 和都是 294）全撞在一起，聚集得一塌糊涂。

    你可能会想：那把 tableSize 改小不就行了？不行——8 个字符一共有 $26^8 \approx 2000$ 亿种可能，1016 个桶远不够用。

---

#### 方法二：只取前三个字符，看成 27 进制数（比方法一好点）

$$f(x) = \big(x[0] + x[1] \times 27 + x[2] \times 27^2\big) \bmod \mathrm{tableSize}$$

思路：把前三个字母当成一个三位 27 进制数（a=1, b=2, ..., z=26），这样理论上 $27^3 = 19683$ 种取值，比方法一的 1016 大了一个量级。

!!! problem "那为什么还是不好？"
    问题出在**实际英语单词的分布很不均匀**。虽然理论上有近两万种三字母组合，但真实英语里常见的前缀其实就那么一小撮：

    - 以 "pre"、"con"、"dis" 开头的词**特别多**（press, prevent, previous... / contain, control, connect... / disable, discover, display...）
    - 而以 "xq"、"zz"、"qq" 开头的**几乎不存在**

    实际统计下来，英语单词前三个字母的不同组合不到 3000 种。也就是说，**就算 tableSize = 10007，超过 7000 个桶永远是空的**。而 "pre" 这种热门前缀的桶里挤满了词——分布一塌糊涂。

    而且还有第二个问题：**如果两个字符串的前三个字母相同，它们就一定碰撞**，后面再长也没区别（比如 "computer" 和 "compression" 前缀都是 "com"）。

---

#### 方法三（较好）：用移位代替乘法

这次让**所有字符**都参与计算，不再只看前三个：

$$f(x) = \left(\sum x[N-i-1] \times 32^i\right) \bmod \mathrm{tableSize}$$

PPT 上的 C 代码实现：

```c
Index Hash3(const char *x, int TableSize) {
    unsigned int HashVal = 0;
    while (*x != '\0')
        HashVal = (HashVal << 5) + *x++;  /* <<5 等价于乘以 32，但更快 */
    return HashVal % TableSize;
}
```

!!! tip "`*x++` 是什么？"
    `x` 是一个指向字符串的指针，`*x` 表示"取出当前字符的 ASCII 值"，`x++` 表示"往后移一个字符"。合起来 `*x++` 就是 **"取出当前字符，然后指针移到下一个字符"**。整个循环就是从左到右一个字符一个字符地处理整个字符串。

    ### 举个例子：拿 "cat" 跑一遍
    初始 `HashVal = 0`：

    - 读到 'c'（ASCII 99）：`HashVal = (0 << 5) + 99 = 0 + 99 = 99`
    - 读到 'a'（ASCII 97）：`HashVal = (99 << 5) + 97 = 99×32 + 97 = 3265`
    - 读到 't'（ASCII 116）：`HashVal = (3265 << 5) + 116 = 3265×32 + 116 = 104596`
    - 读到 '\0'（结束符），退出循环

    最后 `HashVal % TableSize` 得到最终下标。

    本质上算的是：`'c'×32² + 'a'×32¹ + 't'×32⁰`——相当于把字符串看成一个 **32 进制数**，每一位是字符的 ASCII 值。

!!! tip "为什么用 `<<5`（左移 5 位）？"
    `<<5` 等价于乘以 32，但位运算比整数乘法快得多。这个技巧在性能敏感的场合很常见。

!!! warning "方法三的缺陷：长字符串会截断"
    如果 $x$ 很长（比如街道地址 "12345 Main Street, Apt 678"），左移操作会不断把早期字符的位移出 32 位边界——**高位被丢弃，前面的字符信息丢失了**。

## 4. 解决冲突：分离链接（Separate Chaining）

哈希函数再怎么设计，**冲突（collision）都是不可避免的**——鸽巢原理：可能的 key 有 $T$ 种，而哈希表只有 $b$ 个桶，$T \gg b$。

所以我们需要一套**冲突解决策略**：当两个 key 被映射到同一个桶时，该怎么办？

主要有两类思路：

1. **分离链接（Separate Chaining）**：每个桶不限制槽位数量，冲突的元素用**链表**串起来——正文讲这个
2. **开放地址（Open Addressing）**：冲突了就在表里找别的空位——下一节讲

**分离链接的核心思路：** 同一个桶里的元素，用**链表**串起来。每个桶的第一个节点设置成 dummy head，新元素来了就接在链表后面。

这样比固定 $s$ 个 slot 的做法灵活得多——不会出现某个桶的 slot 不够用、另一个桶的 slot 闲置的情况。

（当然，如果哈希函数把大部分元素都塞到同一个桶里，Find 和 Insert 会退化成 $O(N)$——所以哈希函数还是得好好设计。）

!!! abstract "类比：信箱上的便利贴"
    每个抽屉（桶）里贴一张便利贴，新来的关键字就往上添一笔。找的时候，先去正确的抽屉，然后顺着便利贴一个个找。

```c
struct ListNode;
typedef struct ListNode *Position;
struct HashTbl;
typedef struct HashTbl *HashTable;

struct ListNode {
    ElementType Element;
    Position Next;
};

typedef Position List;

struct HashTbl {
    int TableSize;
    List *TheLists;    /* 每个桶对应一个链表 */
};
```

??? success "初始化（InitializeTable）"
    ```c
    HashTable initializeTable(int tableSize) {
        HashTable H;
        if (tableSize < minTableSize) {
            printf("Table size too small");
            return NULL;
        }
        H = malloc(sizeof(struct HashTbl));
        if (H == NULL) Error("Out of space!!!");
        H->TableSize = nextPrime(tableSize);
        H->TheLists = malloc(sizeof(List) * H->TableSize);
        if (H->TheLists == NULL) Error("Out of space!!!");
        for (int i = 0; i < H->tableSize; ++i) {
            H->TheLists[i] = malloc(sizeof(struct ListNode));
            if (H->TheLists[i] == NULL) Error("Out of space!!!");
            else H->TheLists[i]->Next = NULL;
        }
        return H;
    }
    ```

    注意：每个桶都分配了一个**头节点（dummy head）**，方便插入和删除。

??? success "查找（Find）"
    ```c
    Position find(ElementType key, HashTable H) {
        Position P; List L;
        L = H->TheLists[hash(key, H->TableSize)];
        P = L->Next;         /* 跳过 dummy head */
        while (P != NULL && P->Element != key)
            P = P->Next;
        return P;
    }
    ```

??? success "插入（Insert）"
    ```c
    void insert(ElementType key, HashTable H) {
        Position pos, newCell; List L;
        pos = find(key, H);
        if (pos == NULL) {. /* 如果不存在才插入 */
            newCell = malloc(sizeof(struct ListNode));
            if (newCell == NULL) Error("Out of space!!!");
            else {
                L = H->TheLists[hash(key, H->TableSize)];
                newCell->Next = L->Next;      /* 头插法 */
                newCell->Element = key;
                L->Next = newCell;
            }
        }
    }
    ```

    为什么先查再插？**避免重复**——如果 key 已经存在，什么都不做。

## 5. 解决冲突：开放地址（Open Addressing）

**为什么需要另一种思路？** 分离链接用链表来串同一个桶里的元素，但链表有个硬伤——**节点在内存里是分散的**，遍历的时候 cache 疯狂 miss，性能大打折扣。

**开放地址的思路：** 干脆不用链表，冲突了就在数组里**找别的空位**塞进去。所有数据都在连续的内存里，cache 友好得多。

做法：定义一系列哈希函数：

$$h_i(x) = (\mathrm{hash}(x) + f(i)) \bmod \mathrm{tableSize}$$

其中 $f(i)$ 是增量函数——决定了你怎么找下一个空位。

!!! warning "装载密度限制"
    开放地址法要求 $\lambda < 0.5$，否则表太满，查找效率会急剧下降。

```c
void insert(int key) {
    index = hash(key);
    int i = 0;
    while (collision at index) {
        index = (hash(key) + f(i)) % tableSize;
        if (table is full) break;
        else i++;
    }
    if (table is full) Error("No space left");
    else table[index] = key;
}
```

开放地址法具体怎么做，取决于 $f(i)$ 怎么选。

### 5.1 线性探测（Linear Probing）

**增量函数：** $f(i) = i$

简单说：**冲突了就往后一个一个挪**，直到找到空位。

$$h_i(x) = (\mathrm{hash}(x) + i) \bmod \mathrm{tableSize}$$

!!! problem "一个问题：聚集（clustering）"
    ![](附件/Pasted%20image%2020260615232715.png)
    一旦发生一次collision后，之后访问到这个桶（原先应该在这个桶，但是桶里已经有人了）的元素会像**堵车**一样堆在一起。越堵越多，访问次数就越大。

    插入和不成功查找的探测次数 ≈ $\dfrac{1}{2}\left(1+\dfrac{1}{(1-\lambda)^2}\right)$
    
    成功查找的探测次数 ≈ $\dfrac{1}{2}\left(1+\dfrac{1}{1-\lambda}\right)$

    可以看到 $\lambda$ 越接近 1，分母趋近于 0，探测次数爆炸。

### 5.2 二次探测（Quadratic Probing）

为了解决Linear Probing的**Primary Clustering**问题，引入了Quadratic Probing。

**增量函数：** $f(i) = i^2$

$$h_i(x) = (\mathrm{hash}(x) + i^2) \bmod \mathrm{tableSize}$$


### 重要定理

如果 TableSize 是质数且 $\lambda \leq 0.5$，那么对于任意 $0 \leq i \neq j \leq \lfloor \mathrm{TableSize} / 2 \rfloor$，有：

$$(\mathrm{hash}(x) + i^2) \bmod \mathrm{TableSize} \neq (\mathrm{hash}(x) + j^2) \bmod \mathrm{TableSize}$$

即前 $\lceil \mathrm{TableSize} / 2 \rceil$ 次探测的位置全部不同。

**证明：**

假设某两次探测 $i \neq j$ ($0 \leq i, j \leq \lfloor \mathrm{TableSize} / 2 \rfloor$) 落到了同一个位置：

$$(\mathrm{hash}(x) + i^2) \equiv (\mathrm{hash}(x) + j^2) \pmod{\mathrm{TableSize}}$$

消去 $\mathrm{hash}(x)$ 得 $i^2 \equiv j^2 \pmod{\mathrm{TableSize}}$，即：

$$(i - j)(i + j) \equiv 0 \pmod{\mathrm{TableSize}}$$

因为 TableSize 是质数，$(i - j)$ 或 $(i + j)$ 中至少有一个得是 TableSize 的倍数。

但在 $0 \leq i, j \leq \lfloor \mathrm{TableSize} / 2 \rfloor$ 范围内且 $i \neq j$ 时：
- $|i - j| \leq \lfloor \mathrm{TableSize} / 2 \rfloor < \mathrm{TableSize}$，且 $i \neq j$ 时 $|i - j| \neq 0$
- $i + j \leq 2 \lfloor \mathrm{TableSize} / 2 \rfloor \leq \mathrm{TableSize} - 1 < \mathrm{TableSize}$

两者都不可能是 TableSize 的倍数，矛盾。✅

**推论：** 唯一性告诉我们前 $\lfloor \mathrm{TableSize} / 2 \rfloor + 1$ 次探测给出了 $\lfloor \mathrm{TableSize} / 2 \rfloor + 1$ 个互不相同的候选槽位。而 $\lambda \leq 0.5$ 意味着最多只有 $\lfloor \mathrm{TableSize} / 2 \rfloor$ 个槽位被占用——候选比已占用的还多一个，所以**至少有一个候选槽位是空的**。插入一定能成功。

!!! problem "Quadratic Probing的两个缺点"
    **1. 二次聚集（Secondary Clustering）**：虽然解决了线性探测的主聚集，但**散列到同一个桶的多个键，它们的探测序列是完全一样的**（因为 $i^2$ 序列固定）。也就是说，"同一个桶的冲突"依然会以另一种形式聚集——这叫**二次聚集**。
    **2. 扫不全所有桶**：线性探测每次只往后挪一位，所以**一定能扫遍每一个桶**，只要表里还有一个空位就能找到。但二次探测是跳着走的，有些桶可能永远跳不到，导致明明表里还有空位，插入却因为探测序列循环而**宣告失败**。

    因此，一旦 $\lambda > 0.5$ 且 TableSize 不是合适的质数，探测就可能**陷入死循环**——即使表中还有空位也找不到。

**数据结构定义：**

```c
enum KindOfEntry { Legitimate, Empty, Deleted };

struct HashEntry {
    ElementType Element;
    enum KindOfEntry Info;
};

typedef struct HashEntry Cell;

struct HashTbl {
    int TableSize;
    Cell *TheCells;
};
typedef struct HashTbl *HashTable;
```

**查找实现：** 利用递推公式 $i^2 = (i-1)^2 + 2i - 1$ 来避免每次都算乘法。

!!! tip "while 里的两个条件不能换顺序！！！"
    ```c
    while (H->TheCells[CurrentPos].Info != Empty &&
           H->TheCells[CurrentPos].Element != Key)
    ```
    关键在于 C 语言的 `&&` 如果左边为假时右边根本不会执行。

    如果先读 `Element` 再判 `Empty`：

    ```c
    // ❌ 错误写法
    while (H->TheCells[CurrentPos].Element != Key &&
           H->TheCells[CurrentPos].Info != Empty)
    ```

    当一个槽被标记为 Empty 时，我们只改了它的 `Info` 字段（比如设成 0），**但 `Element` 字段里的数据还在内存里没动过**——可能是之前删除留下的旧值，也可能是 `malloc` 分配时留下的随机比特。拿这种垃圾值跟 Key 比，
    
    - 碰巧相等 → 误判为"找到了"
    - 碰巧不等 → 也没意义，而且本来应该在 Empty 处停下继续往下探测了

    正确的顺序是：**先通过 `Info` 确定槽是 Legitimate 的，再去读 `Element` 比较**。空槽就直接跳出循环（意味着 Key 不在表中），省掉一次无意义的读取。
```c
Position Find(ElementType Key, HashTable H) {
    Position CurrentPos;
    int CollisionNum = 0;

    CurrentPos = Hash(Key, H->TableSize);
    while (H->TheCells[CurrentPos].Info != Empty &&
           H->TheCells[CurrentPos].Element != Key) {

        // 递推优化：CurrentPos_i = CurrentPos_{i-1} + 2i - 1
        CurrentPos += 2 * ++CollisionNum - 1;

        // 用 -= TableSize 代替 % TableSize，更快
        if (CurrentPos >= H->TableSize)
            CurrentPos -= H->TableSize;
    }
    return CurrentPos;
}
```

**插入实现：**

```c
void Insert(ElementType Key, HashTable H) {
    Position Pos = Find(Key, H);
    if (H->TheCells[Pos].Info != Legitimate) {
        H->TheCells[Pos].Info = Legitimate;
        H->TheCells[Pos].Element = Key;
    }
}
```

!!! tip "`Legitimate` 是什么意思？"
    回顾一下 `enum KindOfEntry { Legitimate, Empty, Deleted }`：

    - **Legitimate**：这个槽**当前存的是有效数据**
    - **Empty**：这个槽是空的，可以直接用
    - **Deleted**：这个槽的数据被删了，但为了**探测序列不断掉**，标记为 Deleted 而不是 Empty

    `Find(Key, H)` 返回的位置有两种可能：
    
    1. 如果 Key 已在表中 → 返回的位置是 Legitimate 的，`Info != Legitimate` 为假，**什么都不做**（避免重复插入）
    2. 如果 Key 不在表中 → 返回第一个 Empty 或 Deleted 的槽，`Info != Legitimate` 为真，把槽标记为 Legitimate 并存入 Key

!!! example "为什么要有 Deleted 这个状态？举个例子"
    假设 TableSize = 11，`hash(K) = 0`，用二次探测插入 K。探测序列（$i^2$ mod 11）依次是：

    $$0,\; 1,\; 4,\; 9,\; 16 \equiv 5,\; \dots$$

    假设表中位置 1、4、9 已经被占了：

    - i=0 → 位置 0：满了
    - i=1 → 位置 1：满了
    - i=2 → 位置 4：满了
    - i=3 → 位置 9：满了
    - i=4 → 位置 5：**空的** → 把 K 插在这里 ✅

    后来我们把位置 9 的那个数删了。**如果直接把它标记为 Empty：**

    - 下一次查找 K 时：
      - i=0, 位置 0：不是 K → 继续
      - i=1, 位置 1：不是 K → 继续
      - i=2, 位置 4：不是 K → 继续
      - i=3, 位置 9：**Info = Empty！→ Find 直接返回位置 9** ❌

    K 明明在位置 5，但因为探测序列在位置 9 遇到了 Empty 就停了，**永远走不到位置 5**！

    **把它标记为 Deleted 就对了：**

    - 查找 K 时，位置 9 的 Info = Deleted ≠ Empty → 探测序列**不会停**，继续往下走到位置 5，找到 K ✅

### 5.3 双重哈希（Double Hashing）

**核心思想：** 连二次聚集也要干掉——让**探测步长依赖于 key 本身**，而不是固定的 $i^2$。

**增量函数：** $f(i) = i \cdot \mathrm{hash}_2(x)$

$$h_i(x) = (\mathrm{hash}(x) + i \cdot \mathrm{hash}_2(x)) \bmod \mathrm{tableSize}$$

用**第二个哈希函数** $\mathrm{hash}_2(x)$ 来决定每次跳几步——不同 key 的探测序列不同，彻底避免聚集。

!!! warning "对 $\mathrm{hash}_2(x)$ 的两个硬性要求"
    1. **不能为 0**——否则步长为 0，循环永远跳不出去
    2. **必须与 TableSize 互质**——这样才能保证探测序列走遍表中所有槽位，不会漏掉空位

**常用设计：** 让 TableSize 为质数，取：

$$\mathrm{hash}_2(x) = R - (x \bmod R)$$

其中 $R$ 是一个比 TableSize 略小的质数。

**为什么这样设计？证明一下：**

**1. 保证 $\mathrm{hash}_2(x) \neq 0$：** $x \bmod R$ 的取值范围是 $[0, R-1]$，所以 $R - (x \bmod R)$ 的取值范围是 $[1, R]$，最小也是 1，**永远不会是 0**。✅

**2. 保证与 TableSize 互质：** $\mathrm{hash}_2(x) \in [1, R]$，而 $R < \mathrm{TableSize}$，所以 $\mathrm{hash}_2(x) \in [1, \mathrm{TableSize} - 1]$。因为 TableSize 是质数，[1, TableSize-1] 里的每个数都与 TableSize 互质，$\gcd(\mathrm{hash}_2(x), \mathrm{TableSize}) = 1$ 自动成立。✅

**3. 为什么互质就能走遍所有槽？** 假设某两步 $i \neq j$ 到了同一个位置：

$$\mathrm{hash}_1(x) + i \cdot \mathrm{hash}_2(x) \equiv \mathrm{hash}_1(x) + j \cdot \mathrm{hash}_2(x) \pmod{\mathrm{TableSize}}$$

消去 $\mathrm{hash}_1(x)$ 得 $(i - j) \cdot \mathrm{hash}_2(x) \equiv 0 \pmod{\mathrm{TableSize}}$。由于 $\gcd(\mathrm{hash}_2(x), \mathrm{TableSize}) = 1$，$\mathrm{hash}_2(x)$ 在模 TableSize 下有乘法逆元，两边同时乘逆元得：

$$i - j \equiv 0 \pmod{\mathrm{TableSize}}$$

即 $i \equiv j \pmod{\mathrm{TableSize}}$。这意味着前 TableSize 次探测（$i = 0, 1, \dots, \mathrm{TableSize} - 1$）**得到的 TableSize 个位置全部不同**——正好覆盖整个表。这就是双重哈希最重要的性质。✅

!!! example "课上例子：TableSize = 10（合数）会出什么问题？"
    **参数：** TableSize = 10（不是质数），R = 7（质数）。插入 89, 18, 49, 58, 69, 23。

    $\mathrm{hash}_1(x) = x \bmod 10$，$\mathrm{hash}_2(x) = 7 - (x \bmod 7)$。

    前 5 个数都顺利插入了：
    - 89 → $\mathrm{hash}_1 = 9$，位置 9 ✅
    - 18 → $\mathrm{hash}_1 = 8$，位置 8 ✅
    - 49 → $\mathrm{hash}_1 = 9$（被占），$\mathrm{hash}_2 = 7$，$i=1$：$(9+7)\bmod 10 = 6$ ✅
    - 58 → $\mathrm{hash}_1 = 8$（被占），$\mathrm{hash}_2 = 5$，$i=1$：$(8+5)\bmod 10 = 3$ ✅
    - 69 → $\mathrm{hash}_1 = 9$（被占），$\mathrm{hash}_2 = 1$，$i=1$：$(9+1)\bmod 10 = 0$ ✅

    轮到 23：
    - $\mathrm{hash}_1(23) = 3$，但位置 3 已被 58 占了
    - $\mathrm{hash}_2(23) = 5$，于是探测序列：
      - $i=0$：$(3+0)\bmod 10 = 3$（58）❌
      - $i=1$：$(3+5)\bmod 10 = 8$（18）❌
      - $i=2$：$(3+10)\bmod 10 = 3$（58）❌
      - $i=3$：$(3+15)\bmod 10 = 8$（18）❌
      - …一直在 3 和 8 之间来回跳！

    **为什么？** $\gcd(\mathrm{hash}_2(23), \mathrm{TableSize}) = \gcd(5, 10) = 5 \neq 1$，所以探测序列只能访问 $\mathrm{hash}_1(23) \equiv 3 \pmod{5}$ 的位置（即 3 和 8），**永远到不了位置 1、2、4、5、7**——即便它们全是空的。

    **教训：** TableSize 选质数就能避免这个问题——任何非零步长与质数都互质。R 也最好选质数，保证 $\mathrm{hash}_2$ 的值域分布均匀。

!!! tip "双重哈希 vs 二次探测"
    - **优点：** 理论上能产生最好的无聚集分布，接近真正的随机探测
    - **缺点：** 需要多算一个哈希函数，开销更大；而且因为探测位置跳得太散，**对 CPU 缓存不友好**（cache locality 差）

## 6. 再哈希（Rehashing）

**为什么需要再哈希？** 对于开放地址法（尤其是二次探测），如果表太满（$\lambda > 0.5$），查找时间因冲突加剧呈指数级上升，插入甚至可能失败。

**具体操作步骤：**

1. 创建一个新表，容量 NewSize ≈ **原表容量的两倍**（取离该值最近的下一个质数）
2. 扫描原表，将所有有效元素（Legitimate）按新表大小重新计算哈希值
3. 插入到新表中
4. 释放原表内存

$$T(N) = O(N) $$

**时间复杂度分析：**

旧表里有 $N$ 个有效元素（Legitimate）。因为 $\lambda > 0.5$ 才触发的 rehash，所以旧表大小不超过 $2N$。

1. **扫描旧表：** 最多扫描 $2N$ 个槽位，找到所有 Legitimate 的元素 → $O(N)$
2. **建新表：** `InitializeTable(NextPrime(2 * OldSize))` — 分配一整块内存，**一次 malloc**，不依赖 N，$O(1)$
3. **逐条插入新表：** 对新表来说 $\lambda$ 从 0 开始很稀疏，每条插入都是 $O(1)$，共 $N$ 条 → $O(N)$
4. **释放旧表：** `free(OldCells)` — 一次 free，$O(1)$

**加起来就是 $O(N)$。** 而且 rehash 发生得很稀疏——均摊到每次常规插入上依然是 $O(1)$，和 ArrayList 扩容的思路一样。

!!! tip "注意"
    Rehash 之前一定已经做了 $N$ 次普通插入，$O(N)$ 的 rehash 平摊到每次插入上只增加常数代价，所以均摊后还是 $O(1)$。

    不过，**触发 rehash 的那一次插入本身是很慢的**（$O(N)$ 而不是 $O(1)$）。在交互式系统里，如果某个用户的请求刚好触发了 rehash，他的那一次操作就会明显卡一下——其他用户不受影响。

!!! abstract "什么时候触发再哈希？"
    - **装载密度 $\lambda$ 达到阈值**时（比如 $\lambda \ge 0.5$ 或 $\lambda \ge 0.75$）
    - **插入失败**（因死循环或溢出）时

**C 语言实现：**

```c
HashTable Rehash(HashTable H) {
    int i, OldSize;
    Cell *OldCells;

    OldCells = H->TheCells;     // 保存旧表数据
    OldSize = H->TableSize;

    // 分配一个大约两倍大小（取下一个质数）的新表
    H = InitializeTable(NextPrime(2 * OldSize));

    // 将旧表的有效元素重新插入新表
    for (i = 0; i < OldSize; i++) {
        if (OldCells[i].Info == Legitimate)
            Insert(OldCells[i].Element, H);
    }

    free(OldCells);             // 释放旧表
    return H;
}
```
